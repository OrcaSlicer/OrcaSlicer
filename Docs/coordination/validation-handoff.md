# 固定验证与交付任务

2026-09-11 用户确认。当前只交付团队内部验证版本，不安排正式发布、网站上传或商业发布验收。适用于开发任务与固定验证任务之间协作。稳定规则由根目录 AGENTS.md 管理；用户另行要求远程提交时才应用 [团队 SOP](team-integration-sop.md) 的同步、PR 和 CI 流程。本文件不是后台调度服务；只有实际发送任务消息才会启动接收任务。

## 角色与本机登记

- 开发任务实现和修复产品代码，完成必要自检，准备交接，消费验证结果并向用户汇总。
- 固定验证任务负责独立构建、相关自动测试、真实主窗口验收、记录证据，以及已明确授权的打包与推送。产品缺陷交回开发任务；测试环境的可逆准备可自行完成。涉及产品代码的修复形成新版本并返回开发任务，不能只修验证副本就宣称开发版本已修复。
- 两者通过当前环境的 `send_message_to_thread`、`wait_threads`、`read_thread` 等能力协调。优先等待状态变化，不高频读完整对话。当前任务 ID 可读 `CODEX_THREAD_ID`，不可猜测接收方 ID。

运行 `git rev-parse --path-format=absolute --git-common-dir`，读取其下 `codex/validation/registry.json`。登记包括 schema_version、development_thread_id、validation_thread_id、host_id、project_id、development_checkout、validation_checkout、workflow_path、handoff_root、status。该文件留在本机 Git 元数据中，不提交个人任务编号。若登记缺失或任务不可访问，先查询任务确认身份并报告；不静默另建一批任务，也不误报发送成功。

验证工作区首次创建时只是空闲环境，不代表已经包含最新待验收代码。接收每个交接后再加载明确版本。固定任务在无新交接时结束当前轮、等待后续消息；不设置轮询自动化或反复发送“等待中”。

## 交接与版本

每次交接在登记的 handoff_root 下建立唯一目录，例如 `20260911-001-local-color-r1`。请求和回执分别用 `request.md`、`result.md`；同一请求的修复版递增 r2/r3，不覆盖旧证据。先完整准备，再发送消息。

请求至少包括：

| 字段 | 内容 |
| --- | --- |
| 身份 | 交接 ID、来源任务 ID/host、仓库与源码目录 |
| 用户要求 | 本次修改目的、请求原意、允许执行的动作及范围 |
| 版本 | 源提交、分支、dirty 状态；必要补丁、新增文件、逐文件 SHA-256 和依赖说明 |
| 修改点 | 行为前后变化、相关文件、影响入口、普通 Orca 回归范围 |
| 验证点 | 操作步骤、输入模型/测试数据、预期结果、通过条件；成功及必要失败/取消恢复路径 |
| 已有证据 | 已跑命令、结果、版本、日志；失败或仍待验证项 |
| 交付范围 | 是否打包、包格式；是否推送、目标 remote/分支；收费调用的已有预算及已用次数 |
| 限制 | 已知缺陷、平台明确拒绝的具体动作与原始理由、无法执行的环境条件 |

日常验证允许源提交加完整补丁及新增文件清单，无需为了发起验证强制提交。不能仅发送 HEAD 而漏掉未提交修改，也不能默默混入无关工作、凭据或全部生成资产。源码依赖与验证范围不能拆开时，明确说明快照包含的依赖。交接内容写入前后核对哈希，源发生变化则重新准备；接收方再次校验完整性。

内部测试包同样允许“基础 HEAD + 完整补丁/新增文件清单”，不要求先提交、推送、fetch 或切回团队分支。使用 `release/build_internal.ps1 -SourceManifest <manifest.json>`；快照须覆盖全部程序改动并逐文件匹配，保留 `source_clean=false`、快照和产物哈希。删除文件用 `action=delete` 记录；构建中源码或清单变化则该次包无效。未跟踪的临时产物放在 Git 忽略的输出目录，仅可在 `excluded_untracked_docs` 明确列出无关的 `Docs/*.md`。

请求推送或合入的候选才整理成已提交源码并按团队 SOP 同步。远程审核规则不成为本地完整编译和启动的前置条件；无集成远程引用时内部包记录未知，不为此自动 fetch。开发目录之后的修改不能套用旧快照的通过结论。不要对正在使用的开发目录执行 reset、clean 或切换分支来准备验证。

## 独立环境

- 验证固定复用独立 worktree；每轮先保存其未完工作并检查状态，再切换明确的提交或应用经过核对的快照，不能盲目清空。
- CMake 在该 worktree 内独立配置；不复制开发目录的 CMakeCache 或复用可写对象文件、PDB、DLL。可复用匹配版本的只读依赖，以后的验证使用自己的增量构建。
- 程序从独立运行目录启动，使用测试配置和模型副本。构建后处理必须指向该目录，不能删除或覆盖用户运行实例的 Python、DLL 或资源。共享同一桌面时，真实界面操作串行执行。
- 每轮核对实际 EXE、DLL、资源、sidecar 与源码版本；仅编译或启动成功不算功能验收通过。涉及切页、编辑、恢复或导入时，按根 AGENTS.md 检查状态、撤销/重做、历史资产和准备页交接。
- 离线测试先确认提供商访问确实被隔离。用户要求的真实生成遵循主窗口完整旅程及既有预算；新任务不会重置收费计数。密钥只引用本机私有配置，不放入交接正文、日志和包。

## 消息与结果闭环

开发任务发送“验证请求”，带交接 ID、request.md 绝对路径、来源任务 ID、固定版本及动作范围，并明确要求回复来源任务。应调用消息工具，随后用 `wait_threads` 等待或读取紧凑状态；可以继续独立且已授权的工作。请求未完成不能宣布全部完成。

验证任务先核对请求和版本，按接收顺序逐件处理。相同交接 ID 的重复通知只返回既有状态，不重复生成、推送或发布；新版本用新 ID。接收的“结果回执”不进入验证队列。已有记录不完整时核实实际运行/远程状态，不能凭超时重新执行外部动作。

完成、失败或真实阻塞时，写入 result.md 并向请求中的来源任务发送一次“验证结果回执”：交接 ID、被测版本、逐项 PASS/FAIL/NOT_RUN/BLOCKED、实际命令与结果、截图/日志/产物绝对路径及哈希、缺陷复现步骤、建议修复位置和授权消耗。未运行的 GUI 项不能记为 PASS。只有结果记录完整才可标记通过；局部通过和整体未完成应同时说明。

开发任务收到回执后先核对 ID/版本。已消费的重复回执不重复派单。失败则在已有授权内修复，交付新版本复测；通过则向用户汇总。若开发任务当时已空闲，反馈消息可继续该任务处理结果。单纯确认或初始化握手回执不得触发新的验证循环。

用户只要求“验证”时，默认只做相关本地验证；“打包”“推送”“发布”分别按明确要求及已有授权执行，不自动扩大。固定任务不能直接推送 integration、替代非作者审核或人工合入。平台已拒绝的具体操作随请求/结果保留，不能跨任务或更换工具绕过；其他独立准备继续进行。

阻塞回执须分列：实际工具拒绝（时间、命令/动作、原始输出）、脚本/配置前置条件、尚未执行项。没有证据时不猜测 Auto-review 或永久封禁，不把旧记录当作新的拒绝；也不能把“没有尝试”写成“平台再次拦截”。代理不得自行修改安全策略、拆分或换入口执行同一被拒操作。用户通过客户端支持的方式修改审批模式后，核对实际生效状态；只有取得适用于具体动作的正式批准且工具允许，才能按批准范围继续，不能把配置变更直接记为拒绝已解除。命令透明性和测试资源完整性遵循[根 AGENTS.md 的 Windows 本地执行与审批规则](../../AGENTS.md#windows-本地执行与审批2026-09-11)。

## 初始化检查

建立固定任务后，只做一次配置握手：核对本机登记、双方任务 ID、独立 cwd、流程文件可读性；新任务发送初始化回执，原任务核对收到。该握手不启动 Orca、不提交收费任务、不打包/推送，也不算任何产品功能验证。真实验收必须由后续明确版本的交接请求发起。
