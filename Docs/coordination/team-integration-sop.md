## 一次改动怎样进入集成

本节只用于用户明确请求的远程提交/合入。2026-09-11 当前目标是团队内部验证：先在确定源码上完整构建并实际体验；这不要求先提交、fetch、推送、开 PR 或获得远程 CI。当前没有正式发布、网站上传或商业发布验收步骤。缺少远程制品存储也不阻断本地构建和验收。

流程：同步前通知 → 拉取远程 → 在自己的分支合入集成 → 报告同步结果 → 解决冲突、编译验证 → 推送自己的分支、提 PR → 非作者复核与候选 CI → 串行合入 → 集成验证、归档、更新通知。

开发者负责修复冲突与产品行为，CI 负责在确定版本上执行检查，维护人／未来机器人负责推进受保护的集成分支。`AGENTS.md` 放稳定规则，本文放操作步骤，分支保护和自动化落实准入。三个人各用自己的 checkout；同一个目录中切换多个分支不能隔离并行工作。

### 1. 开始与同步

开工时核对目录、分支、HEAD 和工作树。任务应绑定 issue 或清楚的工作项；涉及 `MainFrame`、`Plater`、Contracts、运行时、CMake、依赖或 CI 等共享区域时，先在工作项说明文件和负责人，由维护人协调重叠修改。独立模块可以同时开发和拉取，不必等待所有人“释放拉代码锁”。

准备提交集成前，先发一条同步通知，然后执行下列步骤。以模型生成分支为例，其他人替换成自己的开发线；每一步确认结果再继续，发生冲突时停止后面的命令。

```powershell
git status --short
git branch --show-current
git fetch origin
git merge --no-edit origin/codex/team/model-generation
git merge --no-edit origin/codex/team/integration
git rev-parse origin/codex/team/integration
```

执行 merge 前先妥善保存未提交工作；不能自动清空、覆盖或把无关改动一并提交。同一开发线有多个并行事项时从集成建立 `codex/task/…` 临时分支，每个 PR 只包含一个完整事项。新临时分支尚无远程同名分支时，省略合入自己远程分支的那一步。

通知“同步完成／发生冲突”，记录本次拉取的集成完整 SHA。冲突在自己的分支处理，对受影响行为复核后完成普通 merge commit；不能一律选 ours/theirs。若决定放弃本次合并，应先保存冲突处理进度，再使用标准中止流程。不要强推已共享的长期分支，也不要各自合入 Orca 上游；上游同步走维护人的独立 PR。

### 2. 验证后推送自己的分支

按 [AI 工程导航](../AI_ENGINEERING.md) 选择适用检查：代码改动执行集成校验和相关离线测试，影响原生代码时编译并测试相应模块；构建／依赖／上游变化加宽平台覆盖。主窗口、导入、切片或恢复行为变化需补实际主窗口证据。纯文档改动检查链接、规则一致性和 diff，无须全量应用构建。

```powershell
python scripts/verify_ai_integration.py --json
git diff --check
git rev-parse HEAD
git push origin HEAD:codex/team/model-generation
```

这段命令不代替适用的编译、测试和主窗口检查；应在其通过、工作树内容与记录版本一致后推送准备合入的改动。若仅备份尚未通过验证的工作，可推送自己的分支并保留 Draft PR，注明失败／未验证范围，不能标为 ready。推送被拒说明远程有新提交，重新 fetch、合并并验证，不用 force 绕过。

PR 填写当前完整源 SHA、已同步的集成 SHA、改动和共享文件、验证命令／结果／证据、构建记录与恢复方式。存在依赖时单独写 `Depends-On: #12, #13`，无依赖可省略。PR 的源提交变化后，更新验证与审批；个人机器通过不代替 CI 对合并候选的检查。

### 3. 排队、复核和合入

当前阶段由维护人 `tangjiajie15191661723-web` 按顺序人工合入，飞书服务接通后只辅助排队、核对和通知。至少一位非作者复核；共享区域由对应负责人参与。CODEOWNERS 的模块路径列模块负责人和维护人，共享路径列三人；GitHub 只要求一位匹配 owner 批准，不能代替维护人安排相关负责人复核。

首次切换三人 CODEOWNERS 时，GitHub 按 PR 目标分支上的旧 CODEOWNERS 计算审批资格；只把新名单放在 PR 中不会立即改变该 PR 的 owner 要求。如果目标基线仍只列 `arsenaltj`，应由已获协作权限的另一位成员推送迁移分支并创建 PR、由 `arsenaltj` 非作者复核；最后一次需审批的推送也不能由 `arsenaltj` 完成，以满足最后 push 的非推送者审批。保留必需 CI 和保护规则，不能以修改名单为理由关闭审批。新名单进入集成后再用真实 PR 验证三人复核路径。同事 B 未接受 write 邀请前，模块负责人发起的模块 PR 仍可能缺少另一位有效 owner，不能把填写名单当作三人互审已启用。

轮到 PR 时，核对源 HEAD、最新集成 HEAD 和两者的合并候选。`AI integration checks`、`Team integration candidate`、审批和讨论都满足规则后，使用受保护的 PR merge 操作；长期开发线使用 merge commit。开发者不直接 push 集成，机器人也不以本地强推绕过保护。

任何一端有新提交，旧候选结果立即失效。当前服务不会发起 CI，也不会合并：作者应重新同步最新集成并 push，触发新候选；仅重跑旧事件不保证换成新基点。未来机器人须串行调度最新候选、再次核对两端和审批，按受保护 API 的结果确认合入；API 超时先查询 PR 状态，不能盲目再次执行。

例如 A、B 都基于 I0 验证。A 合入得到 I1 后，B 必须基于 I1 重新形成候选并验证；即使 B 与 A 没有文本冲突，也不能沿用 I0 的绿灯。群里说过“正在合并”不能替代这个约束。

冲突／单个 PR 检查失败交回作者，允许处理其他合格项；依赖的 PR 未合入则等待。当前集成版本本身失败时暂停普通队列，由维护人通过独立修复／revert PR 恢复，该 PR 仍需必要 CI 和非作者复核。不能关闭门禁或 reset 集成来恢复。

### 4. 合入之后

以 GitHub 返回的实际集成提交 SHA 为依据，执行适用的集成构建、测试与冒烟。PR 合并候选的 SHA／包不能直接标成实际集成版本；即使源码树相同，也需明确记录其来源关系。

合入状态与可体验版本状态分开：先标“已合入，集成验证中”，验证通过且产物、清单归档完成后才标“版本可用”。需要原生验证的版本未通过时暂停普通队列。归档失败标为“待归档”，保留原产物并重试上传，不能谎报完成；未来自动队列应等待交付记录完成再推进下一项。纯文档改动可记录“不生成新包，沿用某个已验证版本”，不伪造新编译版本。

## 群通知怎样发

本地 fetch/merge 不会产生 GitHub PR 事件，现有机器人无法自动知道谁开始拉代码。现阶段由开发者发前后通知；后续如增加本地同步助手，再由明确命令触发通知。以下是模板，不是现有机器人支持的新命令。

```text
【开始同步】模型生成 / 工作项 #42
分支：codex/team/model-generation；将同步集成最新版本。
涉及共享文件：ModelGenerationPanel.cpp；重叠修改请在 #42 留言。

【同步结果】工作项 #42
集成基线：<完整 SHA>；结果：无冲突 / 冲突待处理 / 同步失败。
影响范围：……；负责人：……；下一步：解决冲突后编译验证。
```

成功、冲突、中止、失败都要有结果，不只发开始通知。后续推送、CI、合入和构建链接更新同一 PR 卡片，避免逐提交刷屏。飞书暂不可用时把结果留在 PR／工作项中，恢复后补通知；本地同步不因消息故障而损坏或回滚。通知消息本身不是排他锁、审批或成功证据。

服务接通后沿用已实现的限定命令，例如 `@集成助手 提交 PR #42`、`@集成助手 查状态 PR #42`；这些命令当前不会触发自动合入。应用身份、群和凭据配置见 [服务说明](../../tools/team_integration/README.md)。

## 每次编译版本怎样存档

团队登记范围为每次 CI 构建和每次交付团队体验包的构建，成功、失败、取消均留记录。个人 IDE 的临时增量编译不逐次上传；交给团队体验的包须有版本清单。内部验证包允许 dirty 工作树或 detached HEAD，记录基础 HEAD、完整快照及 SHA-256；无需为打包先提交。实际集成版本仍绑定合入后的提交，不将快照冒充集成结果。

| 记录类别 | 保存内容 | 用途 |
| --- | --- | --- |
| 内部快照 | 基础 HEAD、完整变更文件/删除清单及 SHA-256、构建和旅程结果、包哈希 | 同事体验和问题复现，无需推送 |
| PR 候选 | base/head/candidate SHA、构建与测试日志、成功包、清单 | 判断这对版本能否合入；不得标作实际集成结果 |
| 集成版本 | 实际合入 SHA、关联 PR、适用平台包与哈希、验证和归档结果 | 复现问题、回退参照、团队体验 |
| 失败／取消尝试 | run/attempt、准确版本、失败阶段及现有日志 | 追踪失败原因；标明没有可用包 |

统一版本 ID 使用完整身份字段，例如 `integration-<sha12>-windows-x64-Release-<run_id>-a<attempt>`。显示可用短 SHA，清单中保存完整 SHA；重跑增加 attempt，不覆盖旧包或旧记录。若同一 attempt 内产生多个包，加组件名区分。

每条清单至少记录：仓库、类别、完整源／基线／候选／实际集成 SHA（按类别填写）、固定 Orca 上游 SHA、源树是否干净、关联 PR、构建时间、平台／架构／配置、编译器与依赖／运行时版本、CI run/attempt 和日志链接、测试范围／结果／未验证项，以及每个文件的名称、字节数、SHA-256、不可变存储路径和保留期限。先验证上传文件哈希，再将归档标为完成。展示用“最新可用”索引可更新，已有版本记录和包不覆盖。

使用 [内部构建入口](../../release/build_internal.ps1) 和 [内部打包脚本](../../scripts/package_internal_fast.ps1) 的同一套清单／哈希机制。`-SourceManifest` 接受[交接流程](validation-handoff.md)的基础 HEAD 和完整文件快照；不限制分支、不要求 fetch 或推送。遗漏改动、文件哈希不符或构建中版本变化时失败，不以“提交或清空工作树”作为唯一修复方式。每次使用独立空输出目录；`source-snapshot.json`、包清单和哈希与产物保存在一起。无远程集成引用时清单记 null。快照包标记 internal-validation；只有干净的实际集成分支包才标记 integration。

成功打包不等于主窗口验收或集成准入，必须同时阅读该次结果和限制。先在本地保存可复核记录；长期制品存储与自动归档仍待接入，不能以此阻断已授权的内部验证。保存当次实际构建的原包，不重新压缩后沿用旧哈希。包、日志与清单不提交到源码 Git 历史，且不包含 provider 凭据、个人配置、用户图片或生成资料。

建议的初始保留策略（待归档接入时配置）：PR 候选包 30 天；集成包 90 天；每次构建清单和里程碑包存团队 NAS／对象存储长期保留。测试／JUnit／验收证据至少与其支持的包保留同样久；失败／取消日志保留 30 天，清单继续保留结果和已过期标识。存储位置与访问权限尚未选定，选定前保留本机记录。当前 GitHub 仓库公开，内部体验包不上传到匿名下载页或 GitHub Release；团队分享须使用明确授权的内部渠道。

GitHub Actions 的产物会过期，删除 run 也会删除其产物，因此单独放在 Actions 不能保证长期存档。公开仓库的 Actions 日志／产物保留上限为 90 天；上述 30／90 天是建议值，不代表已修改仓库配置。[官方保留策略](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization)、[产物生命周期](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)。
