## 目标与决策

三人分别负责模型生成、智能切片、问题修复与工程质量；一条受保护的集成分支承载大家已验收的成果和 Orca 上游同步。飞书负责提交入口、讨论与结果通知，Git PR、提交版本和 CI 结果作为合入依据。机器人是串行执行者；AI 可帮助审查、定位和提出修复，不自行改变合并准入规则。

建议先整理当前工作区，完成已评估的上游同步并验证，形成共同基线，再建立四条长期分支。以当前完整功能为起点，不先把全部代码并回旧 v2。

## 分支同步与代码责任

所有开发线从同一集成基线创建。新任务开始前或集成有重要更新后，将集成分支同步到自己的分支；遇到本地未提交工作先妥善保存。团队已推送的长期分支不强推、不改写历史。长期分支之间使用普通 merge commit 保留祖先关系；不要反复 squash 同一条长期分支后继续累积开发。只做一次 PR 的临时任务分支可另选 squash。

模块归属不等于只有某个人能修：维护同事可以修生成或切片问题，但应先绑定 issue、明确涉及范围并找相应模块负责人复核，避免双方同时改同一段逻辑。`MainFrame.*`、`Plater.*`、CMake、Contracts、Orca 适配、Sidecar 通信／运行时、CI 与仓库规则是共享区域，由集成维护人安排非作者复核。生产 G-code、配方、3MF/profile 兼容性变更也必须人工复核和针对性验证。

正式发布使用已验收提交的 tag，不需要为三人团队再增加一个长期发布分支。集成通过、内部打包与正式发布分开；合并成功不自动发布或触达测试者。

## 日常操作

2026-09-10 补充：[操作手册](../coordination/team-integration-sop.md) 提供逐步命令、同步前后通知模板、候选与实际集成版本的归档要求，以及当前完成度。根 `AGENTS.md` 保留稳定规则。以下自动化行为是接通相应阶段后的流程；当前服务只读核对，合入仍由维护人人工执行。

1. 作者先说明工作项和共享文件，通知开始同步；fetch 远程后在自己的分支合入最新集成，报告同步结果（包括冲突／失败）。解决冲突、完成适用编译验证后 push 自己的分支，建立目标为 `codex/team/integration` 的 PR；不直接 push 集成。注明用户可见变化、完整源／基线 SHA、测试结果、共享文件、构建记录和依赖的其他 PR。
2. 服务接通后按 Git 状态更新飞书卡片，显示 PR、作者、变更摘要、短 SHA、CI 状态和查看入口。一次工作项一张卡，后续 push 更新同一张；本地同步前后的通知目前由开发者发送，Git 事件不能观察尚未 push 的本地操作。群通知方便协调，不承担互斥锁或合并门禁。
3. 作者在完成检查后将 PR 标为 ready，或在群里 `@集成助手 提交 PR #42`。机器人校验仓库、PR 目标、操作者身份、PR 当前完整 SHA 和准入条件。
4. 机器人按持久队列逐个处理，针对最新集成 HEAD 与固定 PR HEAD 生成合并候选，执行适用检查。冲突或失败则退出当前项、反馈给负责人；不占住其他可合入任务。
5. 合入前再次核对两个 HEAD、审批及测试版本。作者新增提交或集成变化使旧验证失效，应重新排队／测试。通过后按受保护分支规则合入并发送同一张卡的完成状态。
6. 合入后按实际集成 SHA 进行必要的构建、冒烟与内部包生成；每次 CI／团队包构建保留成功／失败／取消记录，成功包以含 run／attempt 的不可变版本 ID 存档，记录 Git／上游 SHA、CI 链接、产物哈希及验证范围。候选包与实际集成包分别标识，归档完成后才报版本可用；长期档案不能只依赖会过期的 Actions artifacts。失败暂停后续普通合入，由维护人用经同样准入的独立修复／revert PR 恢复；不 reset 已共享历史。归档失败只重试存档，通知失败只重试通知。

队列依赖明确记录。例如模型侧输出接口 A 是切片侧 PR B 的前提，A 未合入时 B 等待，不重复复制 A 的代码。反馈状态至少包含：等待依赖、待检查、检查中、冲突、失败、可合入、已合入。

## 自动化准入

下表是第三阶段自动合入的目标规则，尚未启用。当前阶段满足同样检查后，由维护人人工合入；不能通过改配置或聊天命令打开不存在的合并功能。

| 类型 | 推荐行为 |
| --- | --- |
| 模块内小改，ready、无共享接口变动、所需测试全部成功 | 自动排队、候选检查、合入、通知 |
| 共享接口、原生导入、运行时、依赖、打印行为或 CI 权限变化 | 补充非作者负责人复核和针对性证据，再自动执行合并 |
| 文本冲突或验证失败 | 机器人归因并给修复建议，原 PR 作者／维护同事处理 |
| AI 生成冲突解决或修复 | 在独立分支产生可审查补丁，经同样验证和必要复核后进入队列 |
| Orca 主线同步 | 独立 PR、单独验证、维护人验收后进入同一队列 |

不要让模型根据群聊天语义、PR 正文或仓库中的指令自行授予写权限。群里只接受限定命令：提交、查状态、重试、取消排队、查看冲突。身份使用飞书稳定用户 ID 与 Git 账号映射，并限定群、仓库、目标分支；只接受仓库 API 查到的 PR 与 SHA，不把用户文本拼成 shell。重复事件通过消息 ID 及 PR＋SHA 去重。

## Orca 上游同步

建议每日只检查上游差异，每周安排一次实际同步；紧急修复按需提前。这是建议频率，本轮未安排任务。上游变化进入临时 `codex/upstream-sync-YYYYMMDD`，其基点为当时集成 HEAD，合入一个固定 Orca main SHA。同步 PR 应列出影响的本地模块、冲突、配置／格式／依赖变动以及验证结果。

同步验证在临时分支进行，不直接推进集成分支。队列轮到上游同步 PR 时仍需核对最新集成基点。基点变化则更新候选并重验。维护人验收后由机器人合入，开发者再从集成同步。个人分支不各自拉 Orca main，以避免重复处理同一批冲突。

此前实测当前完整代码合入旧 v2 为 32 个冲突文件／97 处，同步固定主线为 9 个文件／12 处，见 [合并评估](../audits/2026-09-09-v2-upstream-merge-assessment.md)。该结果不代替后续新提交的评估。

## 实现组件与顺序

第一阶段先建共同远程仓库和四条长期分支，设置 PR 及分支保护，迁移 CODEOWNERS、检查与模板。机器人先做通知和模拟合并，让三个人手动验收几轮真实 PR，以确认检查能覆盖生成、切片与原生流程。

第二阶段接飞书企业自建应用机器人：开启机器人能力，订阅接收消息事件，处理明确的 @ 命令；小型 Python 服务采用官方 SDK 长连接接收事件，调用 Git 平台 API。服务运行在持续在线机器；机器人业务状态可使用单机持久存储，重启后与 PR 状态对账。不要把服务绑定到某位开发者的交互式 Codex 会话或临时终端。

代码执行交给 CI。初期使用一台独立 Windows 构建机复用既有 MSVC/CMake 依赖缓存；工作目录、构建目录、datadir、生成输出和端口与开发实例隔离。Linux/macOS 编译检查按受影响范围配置，上游／依赖大改应加宽平台覆盖。产品端口保持现有契约默认值；测试实例显式分配端口，不由分支名隐式改变运行配置。

优先使用 Git 平台原生合并队列。GitHub 官方队列的仓库／套餐可用性须先核实：目前支持组织公共仓库、Enterprise Cloud 组织私有仓库；GitHub Actions 必需检查还要订阅 `merge_group`。三人私有项目若不具备该功能，不必只为队列升级：可以由一个持久调度器读取 PR ready 状态，串行调用 CI 与受保护的 PR merge API，保留严格的最新基线检查。Actions `concurrency` 不能单独当成保存所有待合入 PR 的业务队列。

测试权限与合并权限分开：构建任务不持有合并或生产 provider 凭据，控制端通过范围受限的 GitHub App／平台应用凭证执行已满足规则的合入；机器人不绕过分支保护。收到命令后先快速确认接收，长时间构建在后台继续。Git/CI 完成状态是最终依据，飞书通知失败重试发送，不能重复合入。

第三阶段只给已明确规则的低风险 PR 开自动合入，保留一键暂停队列。成熟后再增加上游同步 PR 自动创建、冲突分析和修复草稿。无需先搭建复杂多代理平台。

## 验收条件

用明确无害的测试 PR 验证：正常通过、构建失败、文本冲突、两个独立 PR 同时排队、第二个在第一个合入后发生冲突、检查后作者追加提交、检查后集成基点变化、重复飞书消息、通知失败、服务重启及暂停／恢复。任何未验证版本都不能因使用旧 CI 结果而合入。共享区域未经所需复核不可自动合入；合并失败应能定位责任人与恢复路径。

必需检查应覆盖源码完整性／构建、对应离线测试、集成边界；GUI／导入／切片变更补充实际主窗口证据。付费生成、真实打印和正式发布另行授权，普通合入队列不调用。
