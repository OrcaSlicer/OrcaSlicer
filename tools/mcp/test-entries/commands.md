## `test_speed_dial`
`test_speed_dial.py` · Python, 36 checks · in `sweep.json` as `{"path": "test_speed_dial.py"}`

**Tests:** The Speed Dial's actions as `action_list` and `action_run` give them: that `action_list` lists every one of the 130 actions of `tests/data/speed_dial_actions.json` with the command `tests/data/speed_dial_action_calls.json` gives it, that a section no action is in is refused and settings are listed only when asked for, and that a few actions, run through `action_run` on the Generic Klipper Printer 0.4, each from a state rebuilt by calls, do what a person's pick does: their dialog answered as the row says, their effect read back, the reply naming the action, and the journal keeping an `action_run` step for it with the arguments its command journals. Each action it runs stands for one way an action runs, and is one whose command no other test runs where there is one:
- `calib_retraction`: a person's form that opens a dialog, answered OK, which then makes the project (the Retraction calibration dialog, which no other test opens).
- `add_handy_orcasliced_combo`: a person's form that runs in place and loads several files.
- `help_keyboard_shortcuts`: an action that opens one of the app's windows.
- `view_rear`: an action whose fixed arguments choose what its command does (`view_set {camera: "rear"}`), read back exactly.
- `go_to_tab`: an action that collects a value, which the journal keeps (`{"tab": "preview"}`).
- `take_screenshot`: an action that writes a file (`window_save_screenshot`).
- `sync_presets`: a refused action, which journals nothing.
- `go_to_layer`: an action whose command's schema refuses the value it is given, whose refusal names `tool_describe` for the command.

An action is its command run with fixed arguments as a person's pick, and `action_run` runs every action the same way, so the test runs a few, not all. What each of the 130 adds to its command is checked without running it: `tests/slic3rutils/test_command_catalog.cpp` ([CommandCatalog][SpeedDial]) checks the command each folds into, its fixed arguments, the value it collects and that it is a person's form of its command, against the same fixture. The commands themselves are checked through their tools in their areas' tests. The Speed Dial's own window, opened with Space and picked from by a click, is `test_speed_dial_open`'s and `test_menu_items_refusals`'.

**Starts from:** `start(client)`, which "starts from the Generic Klipper Printer" compares with `{printer: "MyKlipper 0.4 nozzle", process: "0.20mm Standard @MyKlipper", filaments: ["Generic PLA @System"]}`. The setup check `Start Recording's folder is the output folder` points the folder Take Screenshot saves in at the output folder, through the Start Recording dialog. Before each row, `empty()` makes a new project with its changes discarded, shows Prepare's 3D view, deletes filament slots down to one and sets the expert mode, and the row's state builds on that: `two_cubes` adds two 20 mm cubes side by side and selects the first. The list checks read no state: the actions and their commands are the app's own. No action it runs takes the focus from another program, so it runs among the other tests on a job's data folder.

**Leaves:** Start Recording's folder, the output folder, which the runner deletes when the test passes, so that a later capture with no path goes to the default capture folder, as on a new data folder (`folder_or_default()`, `RecordingDialog.cpp`); and an empty project with one filament slot, in the expert mode, which the next test's `start()` sets back to Simple. Its picks are `action_run` calls, which leave the Speed Dial's usage counts as they were. It saves no preset and installs nothing.

**Decides by:** Exits 1 when any check fails.
- Setup: `starts from the Generic Klipper Printer`; `every action has a call in the fixture`; `every action is listed with its command` (`action_list`, read page by page, lists an item for each of the 130 ids, and its `command` equals the fixture's); `an unknown section is refused` (`action_list {section: "No such section"}`, code `invalid_argument`) and `the refusal lists the sections there are` (its `sections` holds "Slice & Export"); `include_settings lists the settings too` (`action_list {include_settings: true, limit: 200}` has a larger `total` than `action_list {limit: 1}`, and its page holds an id starting `orca_setting`: a setting's action has no section of its own in the order, so the settings come first); `Start Recording's folder is the output folder`.
- Common to every row that runs but `sync_presets` and `go_to_layer`: `... its reply names the action it ran` (`ran` == `orca_command:<key>:orca`), and `... the journal keeps its action_run with the arguments its command journals`, an `action_run` step of that id whose inner `args` are `{"tab": "preview"}` for `go_to_tab`, the value given for its input, and `{}`, no `args`, for the others: the calibration action opens its test's dialog (the person's form), and `calibration_generate_test` rewrites its journal entry (`ActionContext::set_journal_args`) only when it runs the test itself, with its parameters or `silent`.
- `calib_retraction`, from `empty`: the dialog titled "Retraction" answered OK; the project's `name` is "Retraction" and it has at least 1 object.
- `add_handy_orcasliced_combo`, from `empty`: the objects' names are exactly "Orca Head", "OrcaCube_v2.drc", "OrcaPlug_v2.drc", "Orca Belly" and "Orca Pedestal", in that order, and no dialog is open.
- `help_keyboard_shortcuts`, from `empty`: a dialog whose title holds "Keyboard Shortcuts" opened; the test closes it.
- `view_rear`, from `two_cubes` and `view_set {camera: "top"}`: `app_state.camera` `elevation` 0 and `azimuth` 90, each to 2°.
- `go_to_tab`, from `two_cubes`, given `{"tab": "preview"}`: `app_state.tab` is `preview`.
- `take_screenshot`, from `two_cubes`: the reply's `path` names a file in the output folder, of more than 0 bytes.
- `sync_presets`, from `empty`: refused, `not_signed_in`; no `action_run` step of its id in the journal.
- `go_to_layer`, from `empty`: "a command action's arguments its schema refuses carry the tool_describe hint": `action_run {id: "go_to_layer", args: {percent: -1}}`, the value the action collects, which `view_set`'s `layer_percent` minimum of 0 refuses, is refused with code `invalid_argument` and its `hint` is "tool_describe {tool: \"view_set\"} gives its parameters"; then `app_state.tab` is still "prepare", and `journal_step()` finds no `action_run` step for it.

**Not checked:**
- The other 122 actions as actions: each is listed with its command here and checked in the catalog's unit test, and its command through its tool in its area's test, so an action whose command and arguments are right but whose run went wrong for it alone passes. `action_run` runs every action by one code path, which the rows here take.
- Commands no test runs, which the rows here leave out: the other eight calibration dialogs (`test_call_forms` opens the temperature test's through its command), the nine other handy models, the size dialog of `add_primitive_*`, the other Help windows (Troubleshoot, Network Test, About, Check for Updates, Migrate Filament Presets, Tip of the Day), the 3D scene benchmark, Reset Window Layout, and the four actions that hand off to another program (`open_wiki`, `open_youtube`, `install_plugin`, `help_open_config_folder`), which open the browser or the file manager and would take the focus from every other app.
- The screenshot is never opened: a blank one passes. The Keyboard Shortcuts window only shows that it opened.
- The calibration's project beyond its name and an object: the test's objects and the settings it changes are `test_presets`' calibration scenarios'.

**To settle in review:**
- That a calibration action's journal step has the id alone, not `{"test": "<name>"}`. The action runs its command's person form (`NativeCommands::with_person_form()`), which opens the test's dialog and journals nothing; only `calibration_generate_test`'s own run, with parameters or `silent`, calls `set_journal_args`, and `ActionContext` puts the action's fixed arguments in the step only in place of such a rewrite. Both are this branch's code (`Tools/PlateTools.cpp`, `McpPersonContext.hpp`, not on `main`). The step with the id alone replays the same, since the action supplies `test`.

**Strength:** Partial — the handy model, the rear view and Go to tab have their effect read back exactly, the calibration loosely, the window only by its title and the screenshot by its file; every action is listed with its command, and the journal step is pinned exactly for every row that runs.

## `test_menu_items_refusals`
`test_menu_items_refusals.py` · Python, 127 checks

**Tests:** What the object and plate commands built from menu items refuse, called directly and picked from the Speed Dial (Space, search, click). Covers Set as Individual Objects, Select All with a gizmo open, target errors, Rename, Delete on the last solid part and on cut objects, Split, Change Type, Assemble on object-list rows, Mirror, Drop, Add Primitive, Auto-Orient on locked or unprintable objects, and the plate commands on a missing plate. For each case it also checks the state left behind.

**Starts from:** `start(client)`, which "starts from the Generic Klipper Printer" compares with `{printer: "MyKlipper 0.4 nozzle", process: "0.20mm Standard @MyKlipper", filaments: ["Generic PLA @System"]}`. Each scenario then makes a new project and adds what it needs, and the checks read only that project, the notices its picks show and the auto-answer rules it sets, which last one session. A pick clicks the app's own row by its label, `<title> from Orcaslicer`, so an action of a plugin an earlier test left, which names its plugin there, is never picked, and the order the Speed Dial's usage counts give its rows changes nothing a pick reads. The undo fixture keeps its mark in the data folder (`mcp/ops_undo_mark.txt`); the test's first `ops_undo.taken()` call of each check sets it and its result is not read, so a mark another test left counts for nothing.

**Leaves:** its last scenario's unsaved project, a cube on the first of two plates, the second named `second`, with the auto-answer rule that cancels the Edit Plate Name dialog, both of which the next test's `start()` clears; the Speed Dial's usage counts (`speed_dial.stats` in `OrcaSlicer.conf`) raised for each action it picked, which order the Speed Dial's rows for the tests after it; the undo fixture's mark.

**Decides by:** Exits 1 when any check fails; all checks print at the end, so an uncaught `McpError` from a setup call exits non-zero with nothing printed.
- Start: `starts from the Generic Klipper Printer`, `presets()` as written above.
- Direct refusals: the error text holds a phrase and, where given, the details' `code` is exact (`gizmo_open`, `nothing_selected`, `one_object_only`, `wrong_selection`, `last_solid_part`, `cut_object`, `one_shell`, `auto_drop_question`, `no_such_plate` ×7, `no_objects_to_orient`, `not_printable` ×2, `not_renamed`).
- State after each refusal: `object_list` `total`, names, part ids and types, selection, `mirrored` flags, plate list (`name`, `locked`, `current`) and `rotation_deg`, all compared exactly with the state before.
- Picks: each presses Space on the 3D view, waits up to 30 s for `window_list` to list the Speed Dial (the shown web dialog with no title), then types the action's title in its search field and clicks its row. Once the app is idle (`app_wait {for: idle}`), the expected notice text is in `app_state.notifications`, or an auto-answer rule's `uses` has risen by exactly 1 (Rename, last-solid-part message, cut question, Auto-Drop, Edit Plate Name). A rule's `uses` is waited for up to 30 s to change, since the object list posts its messages (`show_error()` opens them from `CallAfter`) and one can open after the app reads idle; that wait covers `object_delete {}` on two solid parts too. The state is then read back, for example Assemble on instance rows giving `[("other",1),("Assembly",2)]`. The checks that a pick opened no dialog (Rename's `uses` unchanged) read once the app is idle.
- Notices two picks share: "Select two or more objects first." (Assemble with one object selected, then Assemble on every part row of an object) and "This acts on one object or part at a time: …" (Split to Objects on two instance rows, then Split to Parts on two part rows). Both refusals' notices are regular ones (`menu_info()` answers them as information), which fade about 10 s after they show, so the first can still be open at the second pick, and while it is open the same text pushed again only moves it to the end of the list (`NotificationManager::activate_existing`). So before the second pick of each pair, the test closes the earlier notice; one that has already faded leaves nothing to close. `widget_list` lists each notification as an `imgui_window` node for its ImGui window, `!!Ntfctn<id>`, with its text as a `text` node in it; the test finds the window whose text holds the notice's text and clicks its large invisible close button, which closes the notification in either theme. That button, labelled " ", and the close glyph beside it have labels the listing cleans to nothing and no `##` name, so `widget_list` lists neither and gives them no ref. The test reaches the invisible one with the locator `{imgui: "", window: "!!Ntfctn<id>", index: N - 1}`, which matches the window's unlabelled items in the order they are recorded; `render_close_button()` submits it last. N is the count the same locator without `index` is refused with ("N ImGui items match …; add \"index\""); it is at least 2, the glyph and the invisible button. A short refusal notice draws no minimize button (`m_multiline` with more than 3 lines only). "the earlier notice is closed" then waits up to 30 s, failing when the time runs out, for `app_state.notifications` to hold no notice with the text. After the second pick, its own check reads the text there again.
- Results that run: `object_delete {}` on two solid parts (the remaining part ids, and the reply's `parts` and `kept`), `object_split keep_z` (2 objects, upper piece above 20 mm), the Auto-Drop "No" pick (pieces dropped below 1 mm), Duplicate Plate (`ops_undo.taken()` count 1, and undo restores 1 plate and 1 object), rename to the same name (no snapshot).

**Not checked:**
- `a pick of Change Type with an object selected says to select a part`: notice text only; the object's part types are not read afterwards.
- `object_auto_orient names only what it turned, not an object on a locked plate`: reads the reply alone. Neither cube's rotation is read, so a turn of the locked-plate cube goes unseen.
- Refusals checked by text only, with no code: `Set as Individual Objects on an object of one instance ...`, `object_delete of an object the project lacks names its index`, `object_mirror with no axis is refused by its schema` (any error containing "axis").
- `and takes no undo snapshot` reads the info-level log through `ops_undo.py`. It would pass if snapshots stopped being logged; the Duplicate Plate count-1 check in the same run would catch that.

**To settle in review:**
- The notices the pairs share are regular notices, not error notices that never fade: `menu_info()` (`Tools/ObjectTools.cpp`, from commits not on `main`) answers `too_few_objects` and `one_object_only` as information, as the menu items told them, since the person can select something else and pick again. So the first notice may fade before the second pick, and the close step then finds nothing; "the earlier notice is closed" still reads the text gone before the second pick, and that pick's own check reads it shown again.
- Reaching the close button through a refusal's count is roundabout. Naming the button in the app (`record_named_item` on the close button in `render_close_button()`) would let the test click it by name; that is a change to the app.

**Strength:** Strong — refusal codes and the state after each refusal are compared exactly, and each pick's notice is its own; only a few picks rest on notice text alone.

## `test_preferences`
`test_preferences.py` · Python, 70 checks

**Tests:** `preferences_get`/`preferences_set` against the Preferences dialog. The keys on each tab match the dialog's named controls; the MCP switch and port; a three-key write read back from the call, from `preferences_get` and from the reopened dialog; `restart_needed`; whole-call refusals. Also the backup timer following Auto backup, the downloads folder (call, dialog row, Browse while the dialog is open, a Browse answered with a folder that does not exist), Hide login side panel's live effect on the Home page, and preset sync / stealth mode with no account.

**Starts from:** `start(client)`, which "starts from the Generic Klipper Printer" compares with `{printer: "MyKlipper 0.4 nozzle", process: "0.20mm Standard @MyKlipper", filaments: ["Generic PLA @System"]}`; no check reads a preset. The baseline gives every preference a new data folder's value. The test then sets `auto_arrange` false and `auto_calculate_flush` "color change" in one `preferences_set`, away from the app's defaults so that the write the test checks puts them back to the defaults, and "the preferences start as written" reads back from `preferences_get` those two and the six its checks write from, at a new folder's values: `opengl_fps_cap` 0, `enable_multi_machine` false, `backup_interval` 10, `hide_login_side_panel` false, `sync_user_preset` false and `stealth_mode` false. The MCP switch and port are the launch's (`--mcp`, `--mcp-port`), which the data folder does not store. The two download folders are made in the test's own temporary folder on every run.
